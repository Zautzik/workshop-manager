## Context / decisions made

**Goal:** host the app live and run the data pipeline (WhatsApp worker capture → parser → cost inference → supervisor review queue) on a ~$0 budget.

**Chosen $0 stack** (full checklist with step-by-step: `docs/go-live-checklist-2026-07-10.md`):
- **Hosting:** Vercel Hobby (non-commercial ToS caveat — fine for pilot; later either Vercel Pro, Cloudflare Workers via OpenNext, or self-host the `output: standalone` build on an Oracle Always Free VM).
- **DB/storage:** existing Supabase Free project. Caveats: pauses after ~7 days without API activity (fix: daily Vercel Cron ping of `/api/health`, which does a real Postgres query), **no automated backups** (needs weekly `supabase db dump` or GH Action `pg_dump`), 500 MB DB / 1 GB storage caps. First likely paid upgrade: Supabase Pro $25/mo.
- **WhatsApp:** **Meta Cloud API directly — Twilio was considered and rejected.** Rationale: inbound messages and 24h-session replies are structurally free on Meta (the entire capture pipeline is inbound); Twilio adds ~$0.005/msg middleman fees and its sandbox join-code/72h-rejoin UX breaks the zero-friction capture thesis. Free Meta dev test number = pilot with up to 5 recipient numbers, no business verification. Start Meta business verification early — it's the long pole (days–weeks). Future cost is only app-initiated template pushes (~US$0.005–0.02/msg in LatAm ≈ $3–12/mo at realistic volume).
- **Observability:** Sentry free (already wired via `@sentry/nextjs`; just set `NEXT_PUBLIC_SENTRY_DSN`), UptimeRobot free monitor on `/api/health`.

## Work completed this session (verified: 85/85 vitest, tsc clean, eslint 0 errors)

### 1. WhatsApp Meta adapter (behind an env flag)
The old webhook signature check (HMAC-SHA256/base64 of raw body) matched **neither** Twilio nor Meta and failed closed — real traffic would have been silently rejected. Now:

- **`src/lib/whatsapp-intake.ts` (new)** — shared by both webhooks. `WHATSAPP_PROVIDER=meta` selects: Meta signature verification (`X-Hub-Signature-256: sha256=<hex>`, HMAC of raw body keyed with the Meta **App Secret**) and payload normalization (nested `entry[].changes[].value` envelope → the flat `{from, body, timestamp, ProfileName}` the pipeline processes). Unset/other = `generic` (the legacy custom scheme, kept for curl tests/simulators). Fails closed in all modes.
- **Both routes refactored** (`src/app/api/whatsapp/webhook/route.ts`, `src/app/api/whatsapp/warehouse/webhook/route.ts`): per-message pipeline extracted into `processMessage()` — logic unchanged — so Meta's batched envelopes loop over it. Meta mode always answers HTTP 200 (non-2xx triggers Meta retries → duplicate processing); delivery-status webhooks are acked and ignored. Photo **captions** flow through as the message body (photo captioned "FIN OT-1234 5000 pliegos" works); captionless media is counted ignored.
- **Tests:** `src/lib/__tests__/whatsapp-intake.test.ts` (~20 cases: both signature schemes, tampering, fail-closed, envelope extraction, captions, statuses, batching). `.env.example` documents `WHATSAPP_PROVIDER`.
- **To activate (user-side):** in Vercel set `WHATSAPP_PROVIDER=meta`, `WHATSAPP_AUTH_TOKEN=<Meta App Secret>` (App Dashboard → Settings → Basic), `WHATSAPP_VERIFY_TOKEN=<any random string>`; in Meta App Dashboard → WhatsApp → Configuration set callback `https://<app>.vercel.app/api/whatsapp/webhook`, the verify token, subscribe to the **messages** field. GET handshake was already Meta-shaped — no change needed.
